# SQLite on Android Design Spec

## Problem Statement

The app currently runs PGlite (PostgreSQL compiled to WASM) inside the Capacitor WebView. On-device profiling shows that every IR scan triggers three DB round-trips that each cost ~500 ms on a T23X PDA:

- `getSuppliersWithQrTemplates` (~460 ms)
- `findReceivingCandidates` (~520 ms)
- `findPickingCandidates` (~520 ms)

That is ~1.5 s of the scan-to-dialog latency before any UI work. PGlite WASM is the bottleneck, not missing indexes or query shape.

## Goal

Replace PGlite with a native SQLite database on Android (and iOS if desired) while keeping the web browser demo functional through a web fallback. Expected outcome: DB round-trips drop from ~500 ms to <50 ms, making scan-to-dialog feel instantaneous.

## Decision: Use `@capacitor-community/sqlite`

### Why this plugin

- Mature, actively maintained Capacitor plugin for native SQLite.
- Provides **one JavaScript API** that works on Android, iOS, **and web** (via sql.js fallback).
- Supports JSON storage, encrypted DB, and migration helpers.
- Fits our stack: Capacitor + Nuxt 3 SPA.

### Why not native PostgreSQL on Android

Embedding a real PostgreSQL server process on Android is non-standard, heavy, and adds process-management complexity. SQLite is the de-facto local relational database on mobile.

## Architecture

```
┌─────────────────────────────────────┐
│          Nuxt 3 SPA (Vue)           │
│    pages / composables / services   │
└──────────────┬──────────────────────┘
               │  uses
        ┌──────▼──────┐
        │   useDb()   │  Drizzle-ORM-like thin wrapper
        └──────┬──────┘
               │  SQL + params
    ┌──────────┼──────────┐
    │          │          │
┌───▼───┐ ┌────▼────┐ ┌───▼────┐
│ Android │ │   iOS   │ │  Web   │
│ SQLite  │ │ SQLite  │ │ sql.js │
│ (native)│ │ (native)│ │(fallback)
└─────────┘ └─────────┘ └────────┘
```

We will **not** use Drizzle's SQLite driver because the project already relies heavily on raw SQL and Drizzle's cross-dialect mapping is awkward for our complex queries. Instead:

- Keep Drizzle schema files for TypeScript types.
- Introduce a small `SqliteDatabase` wrapper (`db/sqlite.ts`) that exposes:
  - `exec(sql: string)` for schema init.
  - `query<T>(sql: string, params?: unknown[]): Promise<{ rows: T[] }>` for reads.
  - `run(sql: string, params?: unknown[]): Promise<{ changes: number; lastInsertRowId: number }>` for writes.
  - `transaction(fn: (tx) => Promise<void>)`.
- Replace `composables/useDb.ts` so it returns the `SqliteDatabase` wrapper.
- Replace `plugins/pglite.client.ts` with `plugins/sqlite.client.ts`.

## PostgreSQL → SQLite Migration Notes

### Schema changes

| Postgres construct | SQLite equivalent |
|---|---|
| `uuid` primary keys | `TEXT` (still generated by `uuid` package) |
| `TEXT` | `TEXT` |
| `INTEGER` | `INTEGER` |
| `BOOLEAN` | `INTEGER` (0/1) |
| `TIMESTAMP` | `TEXT` (ISO 8601 strings) |
| `SERIAL` / auto-increment | `INTEGER PRIMARY KEY AUTOINCREMENT` (not needed for UUID PKs) |
| `jsonb` | `TEXT` storing JSON |
| `to_regclass('public.users')` | `SELECT name FROM sqlite_master WHERE type='table' AND name='users'` |
| `COUNT(*)::text` | `CAST(COUNT(*) AS TEXT)` |
| `COALESCE(...)` | same |
| `REGEXP_REPLACE(..., '\s+', ' ', 'g')` | custom `regexpReplace` helper or inline chain of `REPLACE`s |
| `ILIKE` / case-insensitive regex | SQLite `LIKE` is case-insensitive for ASCII; for Unicode use `LOWER()` |
| `RETURNING` | supported in modern SQLite, but sql.js may not; prefer separate SELECT after INSERT/UPDATE |

### Query adaptations

Most `drizzle-orm/sql` raw queries need mechanical translation. The biggest hits:

1. `REGEXP_REPLACE` used in `db/ocrPicking.ts`, `db/putAway.ts`, `services/adapters/pgliteWarehouse.ts`.
2. `to_regclass` table-existence check in the init plugin.
3. `::text` casts.
4. Postgres-specific functions in seed scripts.

We will centralize the translation by:
- Adding `db/sqliteDialect.ts` with helper functions like `regexpReplace(column, pattern, replacement, flags)`.
- Using those helpers in SQL template strings so the same logic works on both dialects (we will only target SQLite going forward, but the helpers make the SQL readable).

## Web Demo Preservation

`@capacitor-community/sqlite` supports web by loading sql.js from a CDN or local asset. We will:

- Install the plugin and enable web mode.
- Copy `sql-wasm.wasm` into `public/assets/` so the demo works offline.
- Keep `runtimeConfig.public.warehouseAdapter = "pglite"` semantics but rename it to `"sqlite"`.

## Seeding

Current seed scripts (`db/seed.ts`, `db/seed-precalc.ts`) generate data and use `db.insert(...)` (Drizzle PGlite API). We will rewrite them to:

- Generate the same data structures.
- Execute bulk `INSERT INTO ... VALUES (...), (...), ...` statements through the SQLite wrapper.
- Use parameterized queries to avoid SQL injection.

## Migration / Data Loss

SQLite is a different database file. There is no automatic migration from PGlite IndexedDB data. Users will need to reset the app data once after the update. We will document this.

## Out of Scope

- Backend API mode (`warehouseAdapter: "api"`) is untouched.
- Feature behavior changes (e.g., scan matching logic) are untouched; this is a storage-layer swap.
- iOS build changes are out of scope unless explicitly requested; the plugin supports iOS, but verification will focus on Android.

## Success Metrics

- IR scan round-trip DB time drops from ~1.5 s to <200 ms on the T23X PDA.
- `pnpm dev` still works in the browser.
- `pnpm generate` + `npx cap sync android` + `./gradlew :app:installDebug` succeeds.
- All existing tests pass after updating them to use the SQLite wrapper.

## Risks

| Risk | Mitigation |
|---|---|
| SQL dialect differences cause subtle bugs | Comprehensive test suite; compare old/new outputs on seed data. |
| sql.js web fallback performance is poor | Acceptable for browser demo; native Android is the target. |
| Large migration surface | Implement behind feature branch; migrate module-by-module. |
| `@capacitor-community/sqlite` plugin limitations | Prototype schema + one query path before full migration. |
