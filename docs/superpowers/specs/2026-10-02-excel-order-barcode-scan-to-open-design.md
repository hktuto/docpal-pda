# Admin Excel order barcode — scan to open on the PDA (design)

Date: 2026-10-02
Spec type: feature design (approved plan: same-day plan file)

## Problem

The admin shipper (receiving order) and picking-list (picking order) Excel
downloads are printed and carried around the warehouse. Opening the matching
order on the PDA today means manually finding it in the list. We want a
barcode printed on the Excel that a PDA operator scans to jump straight to the
order page.

## Decision

- **Payload:** QR code encoding `warehouse://receiving/<id>` or
  `warehouse://picking/<id>`, where `<id>` is the order's UUID route key —
  the same key the PDA routes `/receiving/:id` and `/picking/:id` use.
  - UUID (not `order_no`/`batch_no`): `picking_orders.order_no` is NOT
    unique; the UUID is unambiguous and needs no lookup/search endpoint.
  - Custom `warehouse://` scheme (not `http(s)`): no host/IP is baked into
    the file, so the same Excel works in the bundled APK, the hosted app,
    and dev. The PDA strips the scheme and router-pushes the path.
- **Symbology:** QR. The payload is ~50 chars; a linear Code 128 would be
  long and error-prone. The NLS-MT95 imager reads QR.
- **Excel embedding:** SheetJS (`xlsx`) cannot write images, so the renderers'
  write step moved to **ExcelJS** (`workbook.addImage` → `worksheet.addImage`,
  80×80, `editAs: "oneCell"`), PNG generated by **`qrcode`**. Row content,
  column widths, and `#,##0` number formats are unchanged; the existing
  tests read the output back with SheetJS and still pass.
  - Shipper: QR anchored at the header's last column, row 1; caption
    "Scan to open in PDA" on the blank separator row (A4). The HCC variant
    (`makeShipperRenderer`) inherits it.
  - Picking list: QR anchored at column I, row 1; caption on A11.
- `Renderer.render` became async (`Promise<{fileName, buffer}>`); routes
  `await` it (shipper zip members via `Promise.all`).

## PDA handling

`utils/orderScanRoute.ts` — `resolveOrderScanRoute(value)` trims the scan,
requires the `warehouse://` prefix, a kind of `receiving`/`picking`, and a
single non-empty id path segment. Picking links resolve to the scan
session `/picking/scan/<id>` (it acquires the work lock on mount, so the
operator lands straight on the scan screen); receiving links resolve to
the order detail `/receiving/<id>`. Anything else returns `null`.

Navigation lives in a **global interceptor, `composables/useOrderScanNav.ts`,
mounted once in `app.vue`**, so an order QR works from every page — home
and the order lists register no page-level scanner composable. It listens
on both transports: the scanner-broadcast event, and a keyboard-wedge
buffer that only swallows keystrokes while they can still form an order
link (normal typing and part scans pass through untouched). The router
instance is captured in `app.vue`'s setup — resolving it at event time
throws in Nuxt, which is why the first implementation silently did
nothing. It skips navigation while a scan-fill input is focused (the
scan becomes field text) and ignores redundant-navigation rejections.

`composables/useHardwareScanner.ts` keeps only a **skip-guard** in
`deliver()`: an order-link value never reaches the page's `onScan` (so it
isn't rejected as a bogus part scan) and plays no beep — the global
listener navigates and beeps once.

## Known limitation

Pages that apply the scanner symbology whitelist (`useSupplierSymbologyScope`
on receiving/put-away detail + stock-search, `useBrandSymbologyScope` on the
picking scan page) restrict the hardware decoder to supplier barcode types;
QR may be disabled there. The global order-link interceptor skips navigation
while a form input is focused, so scan the order QR from a neutral page
(home, order lists). Device-side limitation — no code change.

## Out of scope

- Admin UI changes (download links unchanged — the file gains the barcode).
- Camera-based (`RectangleDetection`) capture routing.
