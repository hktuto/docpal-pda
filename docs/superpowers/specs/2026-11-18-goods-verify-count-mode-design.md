# Goods verify — count mode (其它倉每日盤點做法)

Date: 2026-11-18
Status: implemented

## Background

The goods-verify flow (每日盤點 / 查貨) was redesigned 2026-10-17 to a
per-shelf daily movement summary with **one-press pure confirmation** on the
PDA (`docs/superpowers/specs/2026-10-17-goods-verify-shelf-summary-redesign.md`).
That is the **HK way**.

Other warehouses run a different daily-stocktake discipline: the PDA operator
**blind-counts** — the task shows only the shelf and the products, the
operator keys in the quantity they actually find on the shelf, and an
**admin compares** the counted quantities against the system's live totals.
Only when every line matches does the admin confirm the task complete; a
mismatch is **rejected back** to the PDA for a re-count (never an automatic
adjustment).

Warehouse-exclusive differences are configurable, never git branches
(`docs/superpowers/specs/2026-10-09-multi-warehouse-configurable-design.md`),
so this adds a flow-config knob selecting the mode per warehouse.

## Decision

New flow-config knob **`steps["goods-verify"].mode`** (hoisted at merge time
to top-level `goodsVerify.mode`, following the `steps["put-away"]` hoist
pattern):

- `"confirm"` (default) — today's behavior, unchanged (HK).
- `"count"` — blind count on the PDA + admin compare/confirm/reject.

### Status flow

```
pending ──(first count line saved)──> counted ──(admin confirm)──> verified
   ^                                    │
   └──────────(admin reject)────────────┘   (counts cleared)
```

- `pending` — generated by the day-end job; no counts yet (or rejected back
  to this).
- `counted` — at least one count line saved; admin sees submissions live.
- `verified` — admin confirmed every line matches; terminal.

There is deliberately **no `rejected` status**: reject returns the task to
`pending` and clears its count lines, so the PDA queue shows it as an
ordinary un-counted task again. The transition log records the rejection
(actor, timestamp, snapshot of the rejected counts in `metadata`).

### Blind count

In `count` mode the PDA task detail shows **only shelf + product identity**
(`partNo` / `wclItemNo` / `description`) plus a quantity input per line. It
must NOT render `qtyChange` or `currentTotal` — showing system figures would
let operators copy the expected number instead of counting. The system side
of the comparison is visible **only on the admin page**.

### Counted-quantity comparison uses LIVE totals

The admin compares each line's counted qty against the shelf's **current**
`SUM(total_qty)` from `inventory_lots` (computed at read/confirm time), not
the generation-time `movements.currentTotal` snapshot (which goes stale after
later stock moves). The snapshot stays in the payload for reference.

### Per-line immediate submission

There is no task-level "submit". Each line saves independently
(`POST /goods-verify-tasks/:id/counts` `{partNo, qty}` — upsert keyed by
`(task_id, part_no)`), emits SSE, and flips `pending → counted` on first
save. The admin console live-reloads on the same topic.

### Scope of count lines

Only parts present in the task's `movements` jsonb are countable — the task
is exactly "the shelf + products that moved that day". Saving a count for an
unknown part is a 400.

### Server-side mode enforcement

- Count endpoints require `mode = "count"` (409 otherwise).
- The legacy one-press `POST /goods-verify-tasks/:id/verify` requires
  `mode = "confirm"` (409 otherwise) — in count mode confirmation is the
  admin's action, not the operator's.
- Admin confirm/reject require `mode = "count"` + admin group (the routes
  live under `/admin/*`, guarded by the standard admin middleware).

## Schema

New table `goods_verify_task_counts` (migration `0068_…sql`):

| Column | Type | Notes |
| --- | --- | --- |
| `id` | text PK | `app_uuid_v7()` |
| `task_id` | text → `goods_verify_tasks(id)` | |
| `part_no` | text not null | must exist in the task's `movements` |
| `counted_qty` | integer not null | CHECK `>= 0` |
| `counted_by` | text → `users(id)` | |
| `counted_at` | timestamp not null | |
| `created_date` / `last_update_date` | timestamp | convention |

`UNIQUE (task_id, part_no)` + index on `task_id`.

## API

PDA-facing (JWT; mounted on the existing non-admin router):

- `POST /goods-verify-tasks/:id/counts` — body `{partNo, qty}`; upserts the
  line, auto-transitions `pending → counted`; emits
  `goods_verify.count_updated` on `/goods-verify-tasks`; returns the
  refreshed task row. Errors: 404 task, 400 unknown part / non-integer /
  negative qty, 409 verified task or `mode != "count"`.

Admin-facing (new `routes/admin/goodsVerify.ts`, under `/admin`, admin-group
guard):

- `POST /admin/goods-verify-tasks/:id/confirm` — `counted` only; every
  movement line must have a count **and** equal the live shelf total, else
  409 (`goods_verify_task_incomplete` / `goods_verify_task_mismatch`);
  stamps `verified_by/at` + transition log; emits
  `goods_verify.task_confirmed`.
- `POST /admin/goods-verify-tasks/:id/reject` — `counted` only; status →
  `pending`, deletes count lines, transition log with the rejected-counts
  snapshot in `metadata`; emits `goods_verify.task_rejected`.

Reads (extended in place, both consoles consume them):

- `GET /goods-verify-tasks` — rows gain `countsCount`.
- `GET /goods-verify-tasks/:id` — gains `lines` (per part: `qtyChange`,
  snapshot `currentTotal`, **`liveTotal`**, `countedQty`, `countedBy`,
  `countedAt`) and `progress {countedLines, totalLines}`.

## UI

**PDA `pages/goods-verify/[id].vue`** branches on `goodsVerifyMode`
(exposed via `useFlowSteps`, default `"confirm"` — backends predating the
key omit it):

- `confirm` — exactly as today.
- `count` — one card per movement with product identity + numeric input +
  per-line save (packaging `num()` parse pattern; integer ≥ 0 validation);
  saved lines show a ✓ + counted-at; no system quantities anywhere; **no
  confirm button**; subscribes to `/goods-verify-tasks` SSE so an admin
  reject/confirm refreshes the page.

**PDA list** — status chips per mode (`counted` replaces nothing; `skipped`
chip stays confirm-mode-only along with the rest); BUG-048 fixed in passing
(list rows have no `boxId`/`partNo`/`wclItemNo` — client search filters
`shelfCode` only).

**Admin `pages/goods-verify/`** (new, Gen-A pattern after
`internal-transfer-orders`): list (date + status filter, progress column,
`useChangeNotice` on the three `goods_verify.*` types) and detail (lines
table with live total vs counted qty + match/mismatch badge; footer
確認完成 / 駁回 with `window.confirm`; confirm disabled until every line is
counted and matches). Nav entry + `admin.navLinks.goodsVerify` in the three
locales; mode editor (SearchableSelect) added to `pages/flow-config.vue`.

## Events

New SSE types (all topic `/goods-verify-tasks`):
`goods_verify.count_updated`, `goods_verify.task_confirmed`,
`goods_verify.task_rejected`. Added to the PDA `KNOWN_EVENT_TYPES` gate.

## Non-goals

- No automatic stock adjustment — mismatches are fixed via existing flows
  (the pre-2026-10-17 auto-ADJUST model stays retired).
- No assignee scoping on tasks (unchanged — visible to all).
- No `skipped` status wiring (still declared-but-unused).
- No seed change: HK and SZ both default to `"confirm"`; ops flips SZ (or
  any other warehouse) via `/admin/flow-config`.
- Partial-count "submit" state — the admin sees counts as they land
  (`counted` merely means ≥ 1 line); confirm enforces completeness.
