# Allocation Engine

Concepts: `concepts.md` §6. Implementation: `src/db/allocate.ts`.

`src/db/allocate.ts` `allocateAll` — idempotent recompute per `docs/backend/concepts.md` §6 in `picking_orders.priority_seq` order; open qty = `qty − Σ picking_packages`; orders with a live PDA work lock (`POST`/`DELETE /picking-orders/:id/work-lock`, 409 `lock_held`) are skipped. Picking statuses include `allocated` (admin-confirmed allocation lock via the status override — the order is out of `loadDemands`, so its allocation rows survive every wipe/rebuild; repair via Re-allocate) and `skip` (never allocatable, reference-only; entering it releases all rows; override back to `pending` re-enters allocation) — spec `docs/superpowers/specs/2026-09-22-picking-allocated-skip-status-design.md`; the lifecycle beyond that is `picking → picking_finished` (explicit Finish) `→ measuring_finished` (the order's last pending verify task completes) `→ shipped` (derived by shipShippingBox) — spec `docs/superpowers/specs/2026-10-22-picking-status-split-design.md`; the PDA picking list defaults to `allocated`/`picking` (`picking_finished`/`measuring_finished` via the status filter; other statuses stay admin-only) and pages 50 rows at a time with a load-more footer. Shelf-stock sources exclude lots whose `shelf_code` is missing from `shelves` (upstream sync can write such rows past the FK via replication-role writes, and any UPDATE on them then fails the FK check), and the engine never applies `allocated_qty` counter updates to them. The admin manual-allocate paths apply the same exclusion: growing a pin onto such a lot is rejected (409 `shelf_not_found`, per-row in the allocate-form), RESERVE ledger writes on the release side (form releases, remove-allocation, wipe/rebuild reversals, override steals) null the shelf code rather than violate the identical FK on `inventory_transactions`, and `GET /admin/part-availability` stock rows carry `shelfKnown` so the dialog can flag them. Allocation is manual-only (spec `docs/superpowers/specs/2026-11-03-allocation-manual-only-design.md`): mutation routes never recompute — they only consume the reserved rows; UIs converge via the `allocation.computed` SSE event on `/picking-orders`. Pick scans / scan-into-box / package removal / whole-box claim are the deliberate exception (2026-10-20): they do NOT schedule a recompute at all — a pick consumes exactly what its allocation reserved (`reduceAllocation` shrinks the row in the same tx and scans are capped at the allocation qty), so the fleet-wide availability invariant holds without the old per-scan full-fleet rebuild (which cost a multi-second transaction blocking concurrent scans/finishes on the same rows); stale priorities and newly arrived stock wait for the admin's per-order Re-allocate. Exception: `POST /receiving-orders/:id/confirm-arrival` awaits `allocateForReceivingOrder` — the same wipe/rebuild core scoped to the confirmed order's part keys (parts never compete, so unaffected parts are provably unchanged), fast enough to return in the response (`allocation`, null when the scoped run failed — demand stays stale until the next Re-allocate). The scoped core additionally runs dock pre-passes (spec `docs/superpowers/specs/2026-11-05-allocation-dock-match-ordering-design.md`): source preference is shelf lots FIFO first, then dock stock in three ordered passes — (1) PO match (dock rows whose `po_no` equals the demand's PO — item `additional_data.po_no`, fallback order `po_no` — are pinned, date code ignored, partial takes allowed, ledger `txn_reason` `"recompute: po match"`), (2) qty perfect match (a whole receiving order's box rows summed, or a single box/order-level row, exactly equals the demand's dock remainder — but only when every pinned row carries the oldest available dock date code; ledger `"recompute: perfect match"`), (3) dock FIFO. The passes size themselves against a no-write shelf-FIFO simulation and pin `allocations.manual = true` rows in the part-key scope (removable via the admin remove-allocation action), so they outrank `priority_seq` and survive every later wipe — in the order-only picking Re-allocate scope the same passes pin as NON-manual rows of the selected order (there is no cross-order competition inside a single-order run to outrank, and manual pins would leak outside the order and never be wiped by anyone else); shelf lots themselves are never pinned (pure FIFO); `allocateAll` deliberately runs none of these passes. `GET /allocation/status` exposes the background runner — only allocation-snapshot restores queue there now; `allocation.started` fires per runner task, `allocation.finished` per engine run, `allocation.computed` only on net change, for global "allocating" indicators. `POST /dev/allocate` runs `allocateAll` synchronously (token required; the `POST /dev/reset` re-seed endpoint was removed 2026-11-06 — use the `db:seed` CLI). Admin console manual triggers: `POST /admin/picking-orders/:id/reallocate` (awaits `allocateForPickingOrder` — **strictly single-order scope**, spec `docs/superpowers/specs/2026-11-05-picking-reallocate-single-order-design.md`: only the selected order's open items are wiped/rebuilt; demand loading filters `po.id = <order>` with no status/work-lock clause (the route guards already ran, and an `allocated` order's stale rows stay repairable); other orders sharing part numbers keep their allocation rows byte-for-byte and are netted out of dock availability (`loadReceivingSources` subtracts every remaining allocation row, not just manual/work-locked ones, so their holdings can't be double-booked); the dock pre-passes pin as NON-manual rows of the selected order only, so they ride that order's own wipe/rebuild and never leak fleet-wide; 404 unknown, 409 `order_not_open` unless pending/picking/allocated, 409 `lock_held` with holder info). Per-item admin actions: `DELETE /admin/picking-orders/:id/items/:itemId/allocations/:allocationId` (`removePickingAllocation` — deletes one allocation row with lot release + audit; no order-status check, only the work-lock guard; transient, the next recompute may re-allocate) and `GET /admin/part-availability?partNo=&wclItemNo=` (stock lots + receiving orders containing the part across all org/sub-inventory locations). `GET /admin/part-allocations?partNo=&wclItemNo=` lists the part's allocation rows across ALL picking orders (order no/status, qty, manual pin, source location, work-lock flags) — it powers the expandable "allocated" cell in the picking availability modal and the receiving PartSearchModal's related-stock table (`components/AllocationBreakdown.vue`), where an admin can remove another order's allocation directly or **transfer** it: `POST /admin/picking-orders/:id/items/:itemId/allocations/transfer` (`transferPickingAllocation` — one tx shrink/delete of the source row + amend-or-insert a `manual = true` pin on the target item, both-side RESERVE ledger rows `"admin: transfer out/in"`, work-lock guards on both orders, 409 `location_mismatch` outside the item's org/sub-inventory share partition; no recompute scheduled, the pin survives every wipe/rebuild — spec `docs/superpowers/specs/2026-10-14-admin-cross-order-allocation-control-design.md`). Rows flagged `allocations.manual` (pinned via `POST /admin/picking-orders/:id/items/:itemId/allocations` from the admin availability modal, `addManualPickingAllocation`) are preserved by both wipe/rebuild cores and pre-subtracted from the item's auto-allocation demand; `loadReceivingSources` nets them out of dock availability (spec `docs/superpowers/specs/2026-09-15-admin-picking-item-actions-design.md`). The receiving detail mirrors this per item: `GET /receiving-orders/:id` embeds each item's `orgId`/`subInventoryCode` and `allocations` (with picking order no/status) shown with per-allocation remove, and the part-no 🔍 icon opens a combined search + allocate dialog (`components/receiving/PartSearchModal.vue` — it replaces a separate Allocate action) showing the part's open picking demand (`GET /admin/part-demand?partNo=&wclItemNo=`, only rows matching the item's org/sub-inventory via `components/receiving/PartDemandTables.vue`) with per-row qty + Allocate posting manual pinned allocations capped by the receiving item's received qty, plus a read-only related-stock table. Admin status overrides: `PATCH /admin/picking-orders/:id/status` (any→any over pending/allocated/skip/picking/issue/picking_finished/measuring_finished/shipped; steals the work lock, releases all leftover allocations when leaving pending/picking/allocated for a non-holding status) and `PATCH /admin/receiving-orders/:id/status` (any→any; status stamp only — received qty/ledger/put-away untouched, `arrived_at`/`arrived_by` follow the status) — both in `src/routes/admin/flowEdits.ts`, the picking one schedules no recompute (reopening stays unallocated until the admin's manual Re-allocate) while the receiving one awaits the scoped `allocateForReceivingOrder` (scoped failure leaves demand stale until the next Re-allocate), with single + batch UIs on the admin order detail/list pages (specs `docs/superpowers/specs/2026-09-17-admin-picking-status-override-design.md`, `2026-09-22-admin-receiving-status-override-design.md`). UAT allocation snapshot/restore (spec `docs/superpowers/specs/2026-10-26-uat-allocation-snapshot-restore-design.md`): an opt-in job (`UAT_ALLOCATION_RECOVERY=on`; scheduler in `src/jobs/allocationSnapshot.ts`, logic in `src/db/allocationSnapshot.ts`, tables `allocation_snapshot_batches`/`allocation_snapshot_rows` with NO FKs to upstream-managed rows) snapshots all picking `allocations` at `ALLOCATE_BACKUP` (default `17:45:00+0800`; one batch per local date, replacing the day's earlier capture) and restores the latest batch at `ALLOCATE_RECOVER` (default `08:00:00+0800`) after the nightly upstream inventory wipe/re-seed — both use `HH:mm:ss±HHmm` so the server time zone does not affect them, no boot catch-up. Restore matches original UUIDs first, then stable business keys (order id or `order_no` + `line_id`/line-number/part fallbacks; lots by the full natural-lot key; receiving lines by batch/invoice/part/PO/PO-line/carton), skips non-open (`pending`/`picking`/`allocated`) or work-locked orders, validates open qty + source availability, releases conflicting automatic allocations with RESERVE-release ledger rows (`"snapshot restore: release"`), reports manual conflicts instead of stealing them, reuses the ORIGINAL allocation UUID so retries are idempotent (existing rows are no-ops, no duplicate reservation ledger), and afterwards reconciles ALL `inventory_lots.allocated_qty` / `picking_items.allocated_qty` counters set-wise from current allocation rows (including unrestored rows) + `refreshAllocationStatus`; it runs through the serialized allocation runner and does NOT auto-run `allocateAll`. Admin manual endpoints `POST /admin/allocation/snapshot` / `POST /admin/allocation/restore` (in `src/routes/admin/allocation.ts`) expose the same operations; restore persists the structured per-row report (`restored`/`existing`/`skipped` + reason) onto the batch (`report` jsonb, `restored_at`) and emits `allocation.computed`/`allocation.finished` SSE with `scope: "snapshot-restore"`.
