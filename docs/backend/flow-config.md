# Flow Config

The `warehouse_config` row `"flow"` is the runtime flow configuration, served on `GET /config` and admin-editable via `GET/PUT /admin/flow-config`; the `FLOW_CONFIG` env JSON override wins over the row; deprecated `FLOW_STEPS_DISABLED` still maps onto step enablement. Spec: `docs/superpowers/specs/2026-08-10-flow-config-design.md`.

`GET /config` from the `warehouse_config` row `"flow"` (seeded per warehouse, validated at boot); admin-editable at runtime via `GET/PUT /admin/flow-config`; `FLOW_CONFIG` env JSON override wins over the row; deprecated `FLOW_STEPS_DISABLED` still maps onto step enablement. Top-level `allowedOrgIds` (integer array, `[]` = all orgs) scopes picking/receiving/stock/put-away/goods-verify queries to the listed org partitions via `src/db/org-filter.ts`. Top-level `outdatedStockYears` (positive integer, default 2) sets the stock-age threshold for the admin stock-search summary's outdated count (lot canonical YYWW date code older than N years). Top-level `dateCodeFormat` (`"wwyy"` default | `"yyww"`) declares the label/upstream date-code format (spec `docs/superpowers/specs/2026-10-22-datecode-format-config-design.md`): the canonical stored format downstream of receiving is YYWW (year-first — lexicographic order is chronological; `inventory_lots`, `picking_packages`, all rank/sort/filter logic), while the receiving enclave (`receiving_orders`/`receiving_invoice_items` date codes, scan-decode output) stays label format; conversion happens at the enclave boundaries via `swapDateCode`/`toCanonicalDateCode`/`toLabelDateCode` (`src/db/dateCode.ts`, mirrored in `apps/pda/utils/dateCode.ts` and `apps/admin/utils/dateCode.ts`). Backend payloads stay canonical; every operator-facing date-code display in the PDA/admin renders through `toLabelDateCode(code, dateCodeFormat)` (stock search, picking/verify/receiving allocation cells, scan-queue rows — clients still POST label-format scanned codes and only compare in canonical). One-time migration `scripts/migrate-datecode-yyww.mjs` (NOT idempotent); upstream sync must write `inventory_lots` in YYWW (receiving orders stay WWYY). Top-level `receivingSubInventoryRules` (rule groups `{orgIds, patterns: [{poNoPattern, subInventoryCode}], default}` — item enters the group containing its org, first matching `poNoPattern` glob wins (`319*` prefix, `*W` suffix, `*` catch-all), else the group `default`) re-stamps receiving items' `sub_inventory_code` at confirm-arrival, before allocation runs (spec `docs/superpowers/specs/2026-09-02-receiving-subinventory-rules-design.md`; a rule output whose `(org_id, sub_inventory_code)` pair is missing from `org_info` is skipped — the item keeps its value — instead of failing the confirm on the composite FK). Top-level `pickingFromSubinventoryOrgs` (groups `{orgId, fromSubinventories}`) converts transfer picking items (those with `additional_data.from_subinventory`, where the order's pair is the destination) for allocation: org from the group, sub-inventory from the same `receivingSubInventoryRules` evaluated with the item's `additional_data.order_no` (fallback: `additional_data.po_no`, else the group default) under the converted org (spec `docs/superpowers/specs/2026-09-03-picking-from-subinventory-orgs-design.md`). Top-level `dateCodeDisplayTemplate` (default `"[date_code][coo]"`) — admin-display-only template joining a lot's `[date_code]`/`[lot_code]`/`[coo]`/`[cow]` (empty field renders empty) plus `[coo_short]`/`[cow_short]` — the single char from `country_list.short_code` (editable on the admin Country List page; seeded/backfilled as the first letter of the ISO code, unmapped code falls back to the raw code; spec `docs/superpowers/specs/2026-09-22-coo-cow-short-code-design.md`), applied in the admin receiving/picking detail allocation cells; edited on the admin display-config page via `GET/PUT /admin/flow-config` (spec `docs/superpowers/specs/2026-09-17-date-code-display-template-design.md`). Step keys include `labeling` (default enabled, spec `docs/superpowers/specs/2026-10-28-picking-labeling-step-design.md`): when on, a picking finish that matches ≥ 1 active `label_print_rules` row sets `picking_orders.labeling_pending`, queues the order on the PDA `/labeling` pages, and holds its boxes out of measuring/verify until `POST /picking-orders/:id/labeling-finish` clears it.

  Top-level `receivingOrderNameTemplate` (default `"[batch_no]"`) — the receiving order NAME template: placeholders `[batch_no]`/`[invoice_no]` (comma-joined invoice numbers)/`[invoice_no_first]` (first invoice only)/`[supplier_code]`/`[supplier_name]`/`[delivery_date]` (YYYY-MM-DD)/`[date_code]`; the backend renders it into `displayName` on the `GET /receiving-orders` rows + detail (all-empty render falls back to batch_no), consumed by the PDA receiving list/detail titles and the admin receiving list/detail (spec `docs/superpowers/specs/2026-09-21-receiving-order-name-template-design.md`).
  Top-level `pdaListTemplates` (per-list `{title, meta}` templates for the six PDA list pages: `receiving`, `picking`, `put-away`, `goods-verify`, `verify`, `measuring`) — missing lists/fields keep the built-in defaults (= today's rows); resolved onto `GET /config` as `listTemplates` and applied client-side in the PDA (`apps/pda/utils/listRowTemplate.ts` + `composables/useListTemplates.ts`; receiving and put-away `[name]` = the backend `displayName` — put-away candidates/tasks rows carry it from the receiving order; all-empty title → default title → primary id, all-empty meta → line hidden, where "empty" = no letters/digits); edited on the admin PDA view page (spec `docs/superpowers/specs/2026-09-21-pda-list-row-templates-design.md`).
  Top-level `pickingShelfScan` (`"off"` default | `"require-match"` | `"require-any"`) — picking shelf-scan mode (spec `docs/superpowers/specs/2026-10-02-picking-shelf-scan-config-design.md`), resolved onto `GET /config` and edited on the admin flow-config page. `off` = today's behavior (deduction follows the allocation's lot; a shelf scan opens the pick-from-box dialog). In the require-* modes `POST /picking-items/:id/scan` (and `/shipping-boxes/:id/scan`) needs the sticky shelf-scan context (`shelfCode`/`boxId` body fields) on lot-sourced allocations — 409 `shelf_scan_required` when absent — and both modes resolve+deduct the physically-scanned shelf's lot when it differs from the allocation lot's (order org/sub-inventory scope + share members + `allowedOrgIds`, the label's date code must not be newer than the lot's — equal-or-earlier passes, unparseable codes and lots without a date code skip — and the label's lot code must match unless the lot's synced `lot_code` is empty, FIFO by `date_code` — 409 `no_stock_at_location`; `resolveScannedShelfLot` in `src/db/picking.ts`), with package source + PICK ledger on that lot while `reduceAllocation` still shrinks the original allocation. The modes differ only in check strictness: `require-match` rejects early at scan time (the part must have stock on the pending shelf — cached `GET /picking-shelf-stock?partNo=&wclItemNo=&shelfCode=&boxId=&orgId=&subInventoryCode=` → `{qty}` = SUM(total_qty) at the location), `require-any` rejects late at confirm (the 409). On the unified PDA picking page the shelf scan is sticky (one per location visit, banner above the list with clear button; NO pick-from-box dialog in require-* modes), item matching is the normal unfiltered flow in both modes, and OCR capture is allowed with the shelf requirement enforced per matched source after review (dock/receiving sources are exempt).
  Step key `steps["put-away"].skipScan` (boolean, default `false`, spec `docs/superpowers/specs/2026-11-04-put-away-skip-scan-design.md`) — shelve-without-scanning: the PDA put-away detail renders a checkbox on each not-done part-group card; with groups checked, a shelf QR scan shelves every checked group's whole remaining qty onto that shelf without label scans (one `recordPutAwayScan` per member line, batch fields from the receiving declaration, serial null; CN mode stages the pieces locally for the batch confirm). Served on `GET /config` inside `putAway`. HK/SZ seed configs enable it; existing `warehouse_config` rows keep what they have — flip via `PUT /admin/flow-config`.
  Top-level `pdaViewConfig` — the new PDA app view config (spec `docs/superpowers/specs/2026-10-04-pda-app-rewrite-design.md`): `lists` covers the six PDA list pages plus `stock-search` and `labeling` (the 2026-10-28 labeling queue; chip catalog `status`/`allocation_status`/`working_by_name`/`labelCount`/`none`, default `{title:"[order_no]", meta:["[customer_code] · [ship_to]"], chip:"labelCount"}`) with per-list `{title, meta[1–2], chip}` (chip validated against a per-list catalog), and `receivingDetail`/`pickingDetail`/`putAwayDetail` carry `itemFields`/`expandedFields` allow-lists (validated against per-page field catalogs) plus receiving-only `defaultGrouping` (`invoice`/`carton`/`part-no`). It supersedes the deprecated `pdaListTemplates` — a list with no `pdaViewConfig.lists` entry inherits any legacy `pdaListTemplates` customization; the fully-resolved value is served on `GET /config` as `viewConfig` and edited on the admin PDA view page (`apps/admin/pages/pda-view-config.vue` — one section per PDA list/detail page, single shared save) via `PUT /admin/flow-config`.
  Flow step `receiving-cn` (default disabled, spec `docs/superpowers/specs/2026-10-16-customer-receiving-upload-design.md`) — customer receiving (CN) world, exposed on `GET /config` as the boolean `cnReceiving` (a warehouse disables the standard `receiving` step and enables `receiving-cn`): admin uploads a customer receiving Excel (`POST /admin/receiving-cn/excel`, tracking via `GET /admin/receiving-cn`), the backend kicks a DocPal workflow (`src/docpalWorkflow.ts`, Bearer `DOCPAL_WORKFLOW_TOKEN`; workflow ids `DOCPAL_CN_EXCEL_WORKFLOW_ID`, `DOCPAL_CN_PDF_WORKFLOW_ID` reserved for the unimplemented PDF/OCR phase 2), the external upstream-sync service writes the `receiving_orders_cn`/`receiving_invoices_cn`/`receiving_invoice_items_cn` trio, and a status cron (`src/jobs/receivingCnSync.ts`, kill-switch `RECEIVING_CN_SYNC=off`, interval `RECEIVING_CN_SYNC_INTERVAL_SEC` default 120) and the admin confirm (`POST /admin/receiving-cn/orders/:batchNo/confirm`) move the synced order to `scanning` (spec `docs/superpowers/specs/2026-11-01-cn-receiving-scan-design.md`): no `received_qty` fill and no put-away task yet — the PDA 收貨掃描 task (`pages/receiving-cn-scan/`, routes `GET /receiving-cn/scan-tasks[/:id]` + `POST …/scan-aggregate` (server-side aggregate match + FIFO credit across open lines) + `POST …/items/:itemId/flag|reset` + `POST …/finalize`, domain `src/db/receivingCnScan.ts`) resolves the physical goods (`receiving_invoice_items_cn.scan_status`/`scan_qty`/`scan_reason`/`scan_note`/`scanned_by`/`scanned_at`: full cover → `ok`, over-scan/NULL-lineQty credit → `warning`/`qty_mismatch`, partial credit stays open, user flags `missing`/`damaged`/`wrong_part`/`other` → `error` mirrored into the item's mismatch columns), and finalize (409 `unresolved_items` unless `unresolvedAs:'missing'`) stamps the order `in_hand` + creates the dedicated `put_away_tasks_cn` task with `received_qty = min(scan_qty, line_qty)` on non-error credited lines (NULL `line_qty` → `scan_qty`; error/untouched lines stay `received_qty = 0`, so they never enter put-away). PDA manual receiving (`POST /receiving-cn/manual-receipts`, spec `docs/superpowers/specs/2026-10-27-manual-receiving-pda-design.md`) skips the scan step — items are scanned at receipt, so it commits `in_hand` + the task directly. When the step is enabled the PDA put-away flow uses the `/put-away-cn/*` routes (404 while off — a warehouse runs one flow or the other) — the same `apps/pda` put-away list/detail pages branch client-side on the flag (`WarehouseService.listCnPutAwayTasks` / `getCnPutAwayTaskDetail` / `completeCnPutAwayTask`, adapter-normalized to the standard types; local scan staging + sticky-footer batch confirm, no staging endpoints); CN put-away writes single PUT_AWAY `on_hand` ledger rows (no dock row, no `inventory_lot_sources` row), so CN stock only appears in allocation after put-away completes.
